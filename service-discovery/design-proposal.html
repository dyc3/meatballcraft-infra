Architecture proposal · 12 August 2026

Find by broadcast.
Talk by unicast.

A small, reusable discovery layer for OpenComputers programs that lets many instances advertise the same capability without turning every request into a race.

OpenOS 1.8.9 Network Card Lua 5.2 compatible MBC-SD/1

01 / Executive summary

Discovery is a rendezvous, not a transport.

Clients broadcast one short probe on a well-known port. Matching services answer directly to the requesting modem. The client selects an instance and uses that instance’s address for ordinary application traffic.

CLIENT MODEM NETWORK REACTOR A REACTOR B │ │ │ │ ├── broadcast DISCOVER ───────►├────────────────────────►│ │ │ ├──────────────────────────────────────────────►│ │◄─ unicast OFFER A ────────────┤ │ │ │◄─ unicast OFFER B ────────────┤ │ │ │ │ │ │ │ user/config selects “North Reactor” │ │ │ │ │ │ ├── unicast application RPC ───────────────────►│ │ │◄─ correlated RPC response ───────────────────┤ │
Recommendation Adopt one shared discovery protocol and port, while leaving application protocols and ports independent. Discovery returns endpoints; it does not proxy requests or define application payloads.

02 / Scope

What the framework promises

01

Zero-address startup

A client needs a service type, not a component address. One broadcast discovers all reachable instances.

N

Many instances

Multiple reactors, relays, heat exchangers, and future services can coexist on one modem network.

↔

Transport separation

Discovery finds a modem endpoint. RPC, streaming, and control protocols remain application concerns.

≈0

Small footprint

No daemon, registry computer, DNS server, wall clock, or host-only Lua dependency is required.

Non-goals

  • Routing across disconnected modem networks or dimensions.
  • Discovering Linked Card peers. Linked Cards are explicit point-to-point transports and are outside this framework.
  • Authentication, encryption, or protection from hostile computers.
  • Replacing application RPC or guaranteeing application availability.
  • Coordinating globally unique names. Duplicate identities are detected and surfaced, not centrally prevented.

03 / Service model

A stable identity points to a disposable endpoint.

A modem address answers “where is it now?” An instance ID answers “which machine is this?” Keeping both prevents saved preferences from becoming meaningless when hardware is replaced.

RULE 01

Identity is explicit

Services require an instanceId in configuration. The framework must not derive stable identity from a component address or display name.

RULE 02

The sender address is authoritative

Clients record the remoteAddress supplied by modem_message. An offer never supplies its own routable address in serialized metadata.

04 / MBC-SD/1 wire protocol

Primitive fields first, optional metadata last.

Reserve modem port 48700 for discovery. Messages keep routing and compatibility fields in modem arguments, allowing cheap rejection before details are decoded. OpenComputers permits at most eight payload parts, so the display name and metadata share the final serialized details field.

Discovery probe · broadcast

modem.broadcast(
  48700,
  "mbc-sd-v1",                     -- protocol marker
  "discover",                      -- message kind
  requestId,                       -- unique for this client/probe
  "meatballcraft.nc.reactor",      -- requested service type
  1                                -- required application API version
)

Service offer · unicast to probe sender

modem.send(
  clientAddress,
  48700,
  "mbc-sd-v1",                     -- protocol marker
  "offer",                         -- message kind
  requestId,                       -- copied exactly from probe
  "meatballcraft.nc.reactor",      -- offered service type
  "reactor-north",                 -- stable instance ID
  1,                               -- application API version
  48723,                           -- application service port
  serialization.serialize({        -- bounded details (eighth payload part)
    displayName = "North Salt Reactor",
    metadata = {
      zone = "north",
      role = "primary"
    }
  })
)
ValidationRequired behavior
Protocol and kindIgnore unknown values without logging by default.
Request IDAccept an offer only while its matching discovery window is active.

Optional lifecycle messages

Version 1 may support broadcast announce and goodbye messages for responsive UIs, but clients must remain correct without them. Signals can be lost and computers can stop without sending goodbye. An active discover probe is always the source of truth.

05 / Proposed Lua module

A library, not another always-on computer.

Install the reusable module as /lib/meatball/discovery.lua. Providers attach a responder to their existing process; consumers perform bounded discovery at startup or on refresh.

Provider

local discovery = require("meatball.discovery")

local advertisement, err = discovery.advertise(component.modem, {
  serviceType = "meatballcraft.nc.reactor",
  instanceId = "reactor-north",
  displayName = "North Salt Reactor",
  apiVersion = 1,
  servicePort = 48723,
  metadata = { zone = "north" }
})
assert(advertisement, err)

-- Existing application server continues normally.
-- advertisement.close() unregisters the listener when shutting down.

Consumer

local discovery = require("meatball.discovery")

local services, err = discovery.find(component.modem, {
  serviceType = "meatballcraft.nc.reactor",
  apiVersion = 1,
  timeout = 1.0
})
assert(services, err)

-- Each result contains instanceId, displayName, address,
-- servicePort, apiVersion, metadata, and lastSeen.
table.sort(services, function(a, b)
  return a.displayName < b.displayName
end)

Proposed public surface

FunctionContract
advertise(modem, spec)Validate spec, open the discovery port, register an event listener, and return a closable handle.
find(modem, query)Broadcast once, collect matching offers until timeout, deduplicate, and return a deterministic array.
watch(modem, query, callback)Optional follow-up API for dashboards. Maintains a TTL cache and reports add/update/remove events.
Port ownership needs reference counting Multiple libraries in one computer may share port 48700. The module should close it only when the final discovery handle closes—and only if the module originally opened it.

Adopted NuclearCraft services

Advertising programs run an interactive identity setup when no saved configuration or CLI identity is available. They persist the stable ID and display name under /etc/nuclearcraft. CLI --id and --name fields take precedence over saved fields and update the stored configuration.

06 / Operational behavior

Predictable under duplication, loss, and restarts.

Collection window

Default to one second. Do not return on the first offer; that recreates today’s race. Callers may choose a longer timeout for distant or laggy networks.

Deduplication

Deduplicate repeated offers by serviceType + instanceId + address. Refresh lastSeen when the same offer repeats.

Duplicate IDs

If one instance ID appears at multiple addresses in the same window, preserve both results and mark them conflicted. Never silently choose one.

Restart and replacement

Saved preferences store service type and instance ID. Every session rediscovers the current address; cached addresses are hints, not durable configuration.

No response

An empty result is successful discovery with zero services. Transport or argument failures return nil, error.

Rate control

Providers add a small deterministic or random response jitter. Clients debounce manual refresh and should not probe continuously.

Request ID generation

Request IDs need local uniqueness, not cryptographic randomness. Build them from the client modem address, computer.uptime(), and a monotonically increasing process counter. Treat the value as opaque and cap its length.

Compatibility

The protocol marker carries the discovery protocol version (mbc-sd-v1); apiVersion separately describes the discovered application. A future discovery wire format therefore does not force every reactor API to change, and vice versa.

Trust boundary

OpenComputers modem traffic is unauthenticated. Any reachable computer can claim to be a service, observe discovery, or send forged offers. This design is appropriate for a trusted Minecraft network. If control operations are added later, authentication belongs in the application protocol.

07 / Reactor migration

Discovery is only the Network Card fallback.

The reactor client’s transport choice stays simple and precedes discovery: use a Linked Card immediately when one is installed; otherwise discover reactor relays over the modem network.

if component.isAvailable("tunnel") then
  -- Direct, paired transport. No service discovery involved.
  endpoint = rpc.tunnel(component.tunnel, REACTOR_PROTOCOL, TIMEOUT)
else
  -- Network Card fallback. Discover, select, then unicast.
  local services = discovery.find(component.modem, {
    serviceType = "meatballcraft.nc.reactor",
    apiVersion = 1,
    timeout = 1.0
  })
  local selected = selectReactor(services)
  endpoint = rpc.modemUnicast(
    component.modem,
    selected.address,
    selected.servicePort,
    REACTOR_PROTOCOL,
    TIMEOUT
  )
end
  1. Package the discovery module. Add meatball.discovery as a shared library and list it in the relevant OPPM packages.
  2. Name each relay. Store an operator-selected instanceId and displayName in a small configuration file or command-line arguments.
  3. Advertise at the relay. Each relay offers meatballcraft.nc.reactor, API version 1, and its existing application port.
  4. Add a fallback picker. Only when no Linked Card is available, discover for a full collection window and show all relays. Automatically reconnect to the last selected instance ID when it is uniquely present.
  5. Unicast RPC. Extend the modem RPC client to accept the selected remote address instead of broadcasting application requests.
  6. Correlate application calls. Add RPC request IDs so delayed or unrelated responses cannot satisfy the next call. This is adjacent to discovery, but essential for robust multi-client behavior.
Hard boundary The discovery module operates on Network Cards only. It has no Linked Card API, does not advertise Linked Card peers, and never represents a direct link as a discovered or synthetic service. The reactor client alone owns the transport choice shown above.

Rollout compatibility

During migration, a new relay can answer discovery while still serving the old broadcast RPC protocol. New clients use discovered unicast endpoints; old clients continue to work only where a single relay is visible. Remove legacy broadcast RPC after all clients have moved.

08 / Verification

Acceptance tests define the protocol.

  • One probe discovers zero, one, and three providers without returning early.
  • Every provider replies by unicast to the probe’s actual sender address.
  • Concurrent probes receive only offers carrying their own request ID.
  • Duplicate offers from one address collapse into one result.
  • Duplicate instance IDs at different addresses are returned as conflicts.
  • Wrong protocol, service type, API version, request ID, and message kind are ignored.
  • Every discovery packet stays within OpenComputers’ eight-part payload limit.
  • Truncated, malformed, and oversized metadata cannot crash either side.
  • Closing one advertisement does not close a discovery port still used by another.
  • A restarted service with a new modem address is found by stable instance ID.
  • The reactor fixture proves discovery followed by RPC unicast to the selected relay.

Unit-test packet parsing and cache behavior with fake modem events. Extend the existing Ocelot Brain reactor fixture for the end-to-end path. Keep tests independent of Minecraft-only components by stubbing reactor data at the relay boundary.

09 / Decisions requested

Questions for design review

DECIDE A

Identity configuration

Recommended: require a stable, operator-chosen instance ID and a separate display name. Alternative: generate an ID on first run and persist it.

DECIDE B

Discovery port

Recommended: reserve 48700 repository-wide. The exact number is arbitrary, but it must be documented and shared by every package.

DECIDE C

Selection policy

Recommended: reconnect automatically only when a saved instance ID resolves uniquely; otherwise show a picker. Never choose the fastest offer.

DECIDE D

Version-one scope

Recommended: ship advertise and find first. Defer passive watch, announcements, and goodbye signals until a dashboard needs them.

Suggested approval boundary Approve the identity model, wire envelopes, and broadcast-discovery/unicast-application split before implementation. Names, default timeout, and metadata limits can be tuned during test-driven implementation without changing the architecture.
